# Architecture

The system is a strict-TypeScript pnpm/Turborepo monorepo. `web` is a Next.js App Router client, `api` is a NestJS modular monolith exposing REST and WebSocket interfaces, and `worker` owns asynchronous execution without an HTTP server. PostgreSQL is the system of record; Redis supports queues and realtime coordination.

`@customer-ops/config` is the only normal runtime environment boundary for the API and worker. It validates the variables each process currently consumes before startup and returns a typed, narrow configuration object. Local development may load the nearest repository `.env`; production reads the process environment only and never depends on an `.env` file.

`@customer-ops/logger` is the shared operational logging boundary. It owns structured JSON logging, secret redaction, service metadata, and the AsyncLocalStorage request context. The API adapts Nest framework logs to this boundary and owns HTTP-specific middleware and error normalization. The worker and queue infrastructure use the same logger without writing job payloads or Redis credentials.

`@customer-ops/database` is the only PostgreSQL persistence infrastructure boundary. It owns one `pg` pool per consuming process, the Kysely executor, bounded health checks, explicit transaction scopes, deterministic migrations, and connection shutdown. The API receives one runtime through a Nest provider; controllers never construct pools or use the raw driver. API startup validates configuration and constructs the lazy pool but may remain live during temporary PostgreSQL unavailability while `/ready` returns `503`. Production schema changes run as an explicit release step, never automatically during API startup. The worker still has no database-consuming workload in C03.

`@customer-ops/queue` is the only Redis/BullMQ infrastructure boundary. It owns ioredis construction, bounded PING checks, centralized queue naming, producer and worker adapters, job retention defaults, and connection shutdown. The production worker validates Redis configuration, proves connectivity, starts a BullMQ worker with an empty registry, waits for readiness, and then reports itself started. Queue delivery is at least once, retries are explicit and bounded, and side-effecting handlers must be idempotent. `packages/events` remains transport-neutral. The API neither imports nor constructs queue resources in C03, so its health/readiness contract remains PostgreSQL-only.

`@customer-ops/auth` is the transport-neutral authentication core. It owns email/password policy, Argon2id hashing, opaque session-token creation and hashing, authentication orchestration, and PostgreSQL repositories. The API auth module owns cookies, exact-origin CORS, unsafe-route Origin validation, error translation, and the reusable session guard. Raw session tokens are host-only cookie credentials; PostgreSQL stores only their SHA-256 hashes. Authenticated principals contain global `userId` and email only. Sessions do not use JWT or Redis.

`@customer-ops/tenancy` is the transport-neutral organization/workspace core. Organization is the account and commercial container; workspace is the operational tenant boundary in a one-to-many relationship. The package owns Unicode name validation, domain types/errors, repository contracts, executor-bound PostgreSQL persistence, and atomic organization plus initial-workspace provisioning. Its repository binds to an externally supplied transaction so C06 composes owner membership atomically. C05 itself adds no public tenancy controller; C06 exposes guarded routes through the API access module.

`@customer-ops/access` is the transport-neutral workspace membership and RBAC core. It owns membership types and persistence, the six built-in workspace roles, the explicit C06 permission catalog and mapping, server-side access resolution, membership management, final-owner safety, and cross-module organization bootstrap. It depends on database and tenancy boundaries but not on NestJS, authentication, Redis, or BullMQ. The API access module owns the `X-Workspace-Id` transport contract, request attachment, workspace and permission guards, strict request validation, exact-Origin write protection, and safe error translation.

`@customer-ops/teams` is the transport-neutral C07 operational-grouping core. It owns team and team-membership types, Unicode name policy, safe errors, workspace-scoped repository contracts, executor-bound PostgreSQL persistence, lifecycle and eligibility rules, and concurrency-safe conflict mapping. A team membership references a same-workspace C06 workspace membership and never grants workspace access, roles, or permissions. The API teams module reuses the C06 session, workspace-access, permission, and exact-Origin guards; controllers contain no SQL or role comparisons.

`@customer-ops/channels` is the transport-neutral C08 provider-abstraction core. It owns workspace-scoped Channel types, Unicode display-name and opaque identity validation, the code-defined runtime-frozen provider registry, scoped repository contracts, the sole explicit internal global provider-routing resolver, executor-bound PostgreSQL persistence, lifecycle policy, and safe conflict translation. It depends only on database and tenancy boundaries. The API channels module exposes two guarded reads and never exposes raw external identity or a management route. C08 has no real provider, network, credential, webhook, message, Redis, or storage integration.

Workspace is the operational tenant boundary. C07 and C08 operational tables carry `workspace_id`, and every tenant repository requires explicit workspace scope established by the C06 server-side membership lookup; client-supplied identifiers do not authorize access. PostgreSQL enforces same-workspace team relationships and globally unambiguous provider identity claims. The one global channel resolver is internal routing infrastructure, not authorization. Row-level security remains future defense in depth. A C04 authenticated user remains global and has no implied organization/workspace access, role, or permission. C06 request context is separate from the authentication principal and remains free of team or channel selection state. C01 AsyncLocalStorage remains unchanged. External providers belong behind adapters. Durable inbound webhooks and transactional outbox publication remain future work.

Root `pnpm dev` builds shared package dependencies before starting persistent application watchers, so a clean clone does not depend on stale `dist` output. Database access follows ADR-0009, asynchronous infrastructure follows ADR-0010, and authentication follows ADR-0011; remaining module ownership and realtime topology will be specified as their milestones begin. Changes to accepted decisions require an ADR first.
